# 升级指南

本篇面向部署者，说明备份、兼容性变化、账号恢复和上线验收。新部署与配置来源见[部署指南](deployment.md)；维护者的自动检查和隔离验证命令见[开发指南](development.md)。

## 通用升级流程

1. 确认当前版本、目标版本与部署方式，阅读跨越版本的升级说明。记录现有镜像、挂载目录、环境变量来源及反向代理配置，不将凭据写入公开记录。
2. 停止应用和其他写入进程，备份一致的 SQLite、持久化应用配置和本地媒体；默认至少包括完整 `data` 与 `uploads`。远端对象使用独立备份机制。不要在应用写入时只复制单个 SQLite 主文件而遗漏未检查点的 WAL。
3. 在隔离目录恢复备份副本验证启动迁移；移除或替换副本中的生产存储凭据，不能让验证实例继续访问生产对象。使用同一候选版本，不让新旧实例同时写原库或存储。
4. 按原挂载和配置替换应用。镜像部署先拉取固定版本，再停止并重建容器；Compose 源码部署先检出已审阅版本，再执行 `docker compose up -d --build`。不要丢弃原持久化目录或稳定密钥。
5. 检查启动日志、登录 / 改密、历史外链、上传、删除、存储与统计，再完成[部署环境验收](#部署环境验收)。失败时保留日志并停止写入，按[恢复与回滚](#恢复与回滚)处理。

以上步骤不代替实际备份和恢复演练。发布记录中的检查结果不能证明你的代理、存储和资源限制已经验收。

## 按版本检查兼容性

### 从 v3.x 升级至 v4.0.0 与 API v1

这是旧 API 到 `/api/v1` 的破坏性切换：启动迁移清理旧全局 API Token 及其哈希、关闭 `start_api`，移除旧 `setting:api` 权限码。旧凭据不能继续用于 API v1，应在账户设置创建带 scope 的 PAT，并更新客户端。

这是 **v3.x → v4.0.0 / API v1 的历史迁移范围**，不是每次升级都会撤销全部 PAT。兼容清理仍可能在启动时运行，但清理对象是旧全局字段，不是现行正常 PAT。新接口、响应结构和权限使用见 [API 指南](api.md)。

### 升级至 v4.1.2 的视频支持

视频上传默认关闭，需由管理员启用；沿用现有用户和存储桶权限，不影响已有图片流程。关闭上传开关不会停止已有视频读取。

API 继续使用 `/api/v1/images` 和 multipart `images` 字段。统计中的 `total_images` 改为仅图片，视频使用 `total_videos`；趋势 `count` 为图片与视频合计，分别提供 `image_count` / `video_count`。依赖旧统计口径的客户端应调整；历史缺少 MIME 的记录继续归为图片。

视频大小、播放、Range 与体积统计的当前规则见[使用指南](usage.md#视频上传与播放)。

### 升级至 v4.1.3 的安全收紧

保留 API v1、存储类型和历史媒体 URL，但以下行为有意收紧：

- 公共媒体只接受 `GET` / `HEAD`；写请求不能借媒体代理到达存储。已有存储连接测试要求 `storage:update`，更换端点 / 账户需要新凭据。
- 旧浏览器会话需要重新登录。正常历史 PAT 保留；旧默认密码风险账号、改密和管理员重置的撤销规则见[初始化与账号恢复](#初始化与账号恢复)。
- 不再接受新增 SVG、伪装格式或无法验证的图像。图片默认上限 40,000,000 像素、单边 16,384；原图、跳过压缩、URL / 本地导入不能绕过。可通过[进程配置](deployment.md#配置来源与优先级)降低上限，不能从后台调高。
- 全局图像处理并发为 1，繁忙时返回可重试错误。尺寸和并发限制不是硬内存隔离，也不表示消除所有 DoS 风险。
- 新对象不再同名覆盖，删除前检查共享引用，见[对象与存储兼容性](#对象与存储兼容性)。
- 默认不信任转发 IP；代理配置必须显式列出入口，见[反向代理与可信地址](deployment.md#反向代理与可信地址)。限流表每分钟清理过期窗口，最多保留 10,000 个身份；满表且无过期项时返回 `429`，不会淘汰有效窗口来接纳新身份。

完整更新摘要见 [v4.1.3 发布说明](https://github.com/mikusaa/oneimg/releases/tag/v4.1.3)。涉及历史 SVG 时还必须检查应用以外的全部访问出口，不能只升级容器。

### 升级至 v4.2.0 的存储停用与删除

v4.2.0 新增存储停用，并调整删除存储的行为：

- 数据库 `buckets` 表在启动迁移时新增 `disabled` 列，已有存储默认均为启用。
- 删除存储默认**保留**远端物理文件，只删除数据库记录、标签关联和用户授权。旧版本调用 `DELETE /api/v1/storage-buckets/{id}` 会同时清理远端文件；仍需要清理的脚本必须改为显式传 `purge_objects=true`，否则会在远端留下不再被 OneImg 管理的文件，需要自行清理。
- 删除或停用当前系统默认存储返回 `409 storage_is_upload_default`。旧版本会把默认存储静默改回本地存储；现在需先在设置中切换默认存储。
- 向已停用存储上传或导入返回 `409 storage_disabled`；把默认存储设为已停用存储返回 `422 storage_disabled`。

回滚限制：旧版本不认识 `disabled` 列，回滚后已停用的存储会重新出现在上传选项中并接受上传；旧版本删除存储时也会直接清理远端文件。回滚前应先启用或妥善处理停用的存储，并告知管理员删除行为的差异。

完整更新摘要见 [v4.2.0 发布说明](https://github.com/mikusaa/oneimg/releases/tag/v4.2.0)。

### 升级至 v4.2.0 之后版本的存储路径校验

本节适用于 v4.2.0 之后包含存储路径校验的版本：

- 修改存储路径（`default_path`）或文件名模板（`file_name`）时会校验：不支持的变量（变量区分大小写）、不成对的花括号和控制字符都会被拒绝；存储路径还不能包含空格、`\`、`.` 或 `..` 目录。不合规时返回 `422 validation_error`，`errors[].field` 指明字段。已保存的值不会重新校验，可以继续使用，下次修改时再改成合规的值。
- 本地存储的新文件始终写在 `uploads` 目录下。存储路径不以 `uploads` 开头时会自动补上，例如 `/img/{year}` 的新文件实际存放在 `uploads/img/2026/…`，链接也随之变化；已有文件的位置和链接不变。S3、R2、FTP、WebDAV 仍按原样使用配置的路径。
- 所有存储上传时会忽略路径中的 `.` 和 `..` 目录段，`\` 按 `/` 处理。

**升级前检查**：在“系统设置 → 存储与上传”确认存储路径是否以 `/uploads` 开头。如果不是，并且使用过本地存储，旧版本会把文件写在程序工作目录下的对应目录（标准镜像为 `/app/<目录>`），不在 `data` 和 `uploads` 挂载内，重建容器时会丢失。升级或重建容器前，先把这些目录从当前容器复制出来备份，并为它们增加绑定挂载，保证已有文件在原位置继续可读；之后新上传的本地文件会进入 `uploads`。

回滚限制：旧版本不校验这两项设置，本地存储的新文件也会重新按配置写到 `uploads` 之外；已经写入 `uploads` 的文件旧版本可以继续读取。

## 初始化与账号恢复

### 新安装

默认用户名为 `admin`。`DEFAULT_PASS` 为空或仍为旧模板的 `123456` 时，生成独立随机密码，存入 SQLite 同目录的 `.initial_admin_password`，权限 `0600`，日志只提示位置。标准容器路径的读取命令为：

```bash
docker exec oneimg cat /app/data/.initial_admin_password
```

首次登录必须改密，即使显式配置了其他初始密码也不例外。`DEFAULT_USER` / `DEFAULT_PASS` 只用于初始化新库，不会重置已有正常账号。改密后初始密码文件不能当作当前密码来源。

### 历史默认密码账号

当历史 ID `1` 账号仍使用 `123456` 时，启动将其置为受限状态，并在数据库同目录生成 `.admin_recovery_code`。标准容器中由有权操作服务器的人读取：

```bash
docker exec oneimg cat /app/data/.admin_recovery_code
```

受限账号只能通过浏览器会话查看 / 修改自身账户或退出，不能进行正常管理、使用 PAT 或注册 Passkey。在账户设置中同时提交当前密码、新密码和本地恢复码；仅知道旧默认密码不足以恢复管理权限。

成功恢复会消耗挑战、撤销全部 PAT 和历史 Passkey，使旧会话失效。之后重新登录、创建必要的新 PAT，并重新注册可信 Passkey。本地恢复文件在事务提交后尽力删除，即使删除失败也不能重放该挑战。

有效恢复码在正常重启时保持不变；缺失、损坏或权限不安全时会重建，失败则停止启动。不要公开恢复码、手工清空数据库中的受限字段，或反复删除文件绕过恢复流程。

### 会话与 PAT 何时失效

| 操作 / 情况 | 结果 |
| --- | --- |
| 升级后，旧浏览器会话缺少认证版本 | 需要重新登录 |
| 正常历史 PAT 的版本迁移 | 保留，不要求全部重新创建 |
| 历史默认密码风险账号被置为受限 | 旧 PAT 撤销，旧会话失效 |
| 普通改密或管理员重置密码 | 目标用户全部旧会话和 PAT 撤销；普通改密保留 Passkey |
| 完成历史默认密码恢复 | 除撤销会话和 PAT，还删除历史 Passkey |
| 仅修改用户名 | 不批量撤销 PAT |

改密或重置后，应为 PicGo 等客户端创建并重新配置 PAT，协议未改变。不轮换 `SESSION_SECRET`、`CONFIG_SECRET` 来代替账号恢复，也不要恢复旧数据库来“找回”已撤销的令牌。

## 对象与存储兼容性

历史 URL 和文件不自动复制、移动、重命名或删除。启动若发现共享物理对象只报告数量；已经发生同名覆盖的原内容只能从备份恢复。

新对象名称包含 128 位随机身份，主图与缩略图共用该身份，原始文件名仍保留为元数据。对象创建与删除有以下边界：

- 本地使用排他创建，S3/R2、WebDAV 使用 `If-None-Match: *` 条件创建，冲突最多尝试三次；不支持条件语义时拒绝，不能降级为覆盖写。
- S3 兼容服务是否真正执行条件创建，需在隔离存储验证。FTP 使用随机名和写前列目录检查，不是原子条件创建，不能宣称同等保证。
- 配额或数据库事务失败，只清理本次明确成功创建的对象；网络结果不确定时记录待核查孤儿 key，不盲目删除。需监控并人工核查这些日志。
- 删除文件或整个桶前检查跨桶、主图 / 缩略图交叉引用。共享对象仅删除当前记录与关联，最后引用删除时才清理物理对象；计量仍按记录口径。

默认采用单实例，相关锁只协调同一进程，不提供跨实例互斥。不要让新旧容器、导入命令或其他写入工具并行操作同一数据库和存储。

## 历史 SVG 出口与缓存

新增 SVG 被禁止，但历史 SVG 保留文件和原 URL。应用代理对历史 SVG 的读取、部分响应和缓存验证响应设置严格策略：

```text
Content-Type: image/svg+xml
X-Content-Type-Options: nosniff
Content-Security-Policy: sandbox; default-src 'none'; script-src 'none'; style-src 'unsafe-inline'; img-src data:; object-src 'none'; base-uri 'none'; form-action 'none'
Cache-Control: no-cache, max-age=0, must-revalidate
```

普通内联图形仍可展示，依赖外部脚本、字体、图片、表单或嵌入页面的表现不保证保留。

使用 `CDNDomain`、`PublicImageDomain`、静态服务器、对象存储直链或其他绕过应用的出口时，必须在每个出口配置等价策略并清除旧 SVG 缓存。应用不能为外部服务补头，浏览器已有长期缓存的旧响应也存在过渡风险；不能宣称升级应用就立即撤销所有旧缓存的执行能力。

## 部署环境验收

下面是部署者上线前的检查，不等同于维护者的自动测试。先在隔离副本与经授权的测试存储完成会产生写入的验证，再检查实际入口；不对生产媒体或生产存储运行破坏性测试。

- **账号与配置**：验证备份恢复、启动迁移、初始改密 / 历史恢复、正常 PAT 保留与改密后撤销；确认稳定密钥和实际生效的配置来源。
- **代理与访问出口**：确认真实代理地址和转发头覆盖，核对历史外链、公开 `GET` / `HEAD`、单段 Range，以及所有 SVG 出口与缓存清理。
- **真实远端存储**：对将使用的 S3/R2/WebDAV/FTP 服务另行验证新对象创建、同 key 冲突后旧字节不变、读取、失败清理和不确定写结果；本地模拟不能替代。
- **目标容器资源**：在与部署相同的架构、镜像和资源限制下验证正常 24MP / 40MP 图片，记录输入 / 输出、RSS、cgroup 峰值和 OOM 情况。方法见[内存探针](development.md#目标容器内存探针)，实测值不是最坏输入上界。

完成后关注 `405`、`password_change_required`、旧凭证失效、格式 / 尺寸拒绝、处理繁忙、对象冲突与孤儿清理日志，避免记录密码、认证头或解密配置。发布源码和镜像不代表所有部署环境已完成验收，也不代表全仓安全认证。

## 恢复与回滚

恢复前停止写入并保留故障现场，在隔离环境核对数据库、配置和媒体版本是否一致。稳定的 `CONFIG_SECRET` 丢失或改变会导致既有加密数据无法读取；不要用新密钥覆盖原值。

功能回滚只使用保留上述安全边界的构建，不直接重新暴露已知漏洞版本。不把旧库覆盖到当前环境来撤销已经完成的改密或令牌撤销，否则可能重新激活攻击者凭证。

需要从灾难备份恢复时，应隔离恢复并重新处理凭证撤销、存储一致性和安全验收后再开放入口，不能把“能启动”当成安全回滚完成。不要让新旧版本同时写同一库或存储。
